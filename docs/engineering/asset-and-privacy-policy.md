# Assets, ownership, and privacy

## Asset provenance

Prefer original procedural geometry and original synthesized audio. Every external or generated asset needs an entry in the [asset register](../assets/asset-register.csv) with source, creator, license/permission, modifications, attribution, and status.

An available download is not automatically permission to redistribute it. Verify compatibility with hosting, demo publication, and competition requirements. Keep license notices with the asset or in a consolidated attribution file when assets are introduced.

No open-source source-code license has been selected for this repository. Do not add a license or claim that all content is freely redistributable without the owner's decision. Dependency licenses remain their own terms.

## Data minimization

The planned application stores puzzle progress and preferences in browser-local storage. No names, emails, microphone recordings, camera frames, or raw hand poses need to be stored. No analytics, login, advertising, remote database, or payment features are planned.

Hand input is used transiently by WebXR/IWSDK for interaction. That does not mean the hosting provider collects no request data: confirm host logs and platform behavior before writing a final privacy notice.

Browser permissions should correspond to implemented features. Do not request microphone, room scanning, location, or gaze information for the baseline.

## Repository hygiene

Do not commit verification documents, ID images, private participant contact details, environment files, credentials, or local recordings. A future privacy notice and attribution page must describe actual implementation, hosting, and used assets rather than copying these plans as completed facts.

## Public materials

Use footage of the actual application or clearly labelled emulator capture. Avoid unrelated brands, copyrighted songs, identifiable third parties, and invented claims about hardware testing. Check the official content rules before final submission.
